# Analyze evaluation results

Start from the question and existing evidence. Read local `metrics.json`, `summary.jsonl`, and relevant trajectories, or use `osmosis --json eval info <run-name>`. For platform sample outcomes, `osmosis --json eval download <run-name> --type summary --output <fresh-directory> --yes` downloads the summary without all trajectories. Fetch selected evidence with `--type trajectories,artifacts,logs --rows <indices>` when needed. Check installed `--help` for supported selectors, preserve earlier snapshots, and mark incomplete downloads or running results. Run `eval download` from the repository connected to the source workspace, even when writing to an absolute output path. For `eval info` outside the repository, use root `--workspace <name>`.

1. Establish comparability: dataset content and selected row identities, model/checkpoint, rollout revision, grader/verifier and threshold, attempts, and material execution settings. Keep these matched except for the component being compared. A shared dataset name or equal row count does not prove identical examples. Report mismatches before drawing a ranking.
2. Account for outcomes: requested rows and attempts, observed coverage, graded passes and failures, ungraded/errors, timeouts, skips, and pending work. State each rate's numerator and denominator. Missing rewards are not graded zeroes; distinguish quality among graded samples from completion reliability. If useful, report an end-to-end success rate separately with its explicit denominator. Never present a rate over survivors as full-run quality.
3. Compare paired outcomes on matched rows and attempts where available, with category counts when the data supplies categories. If missingness differs, show the matched result and coverage differences alongside the aggregates; do not silently drop hard or failed examples. Use reported Pass@k only with its definition and available attempt counts; a small sample or different k limits the claim.
4. Inspect representative regressions, improvements, and ungraded cases before assigning causes. Separate task mistakes, grader/verifier defects, and runtime/provider failures. Report what the trajectory demonstrates, the remaining hypothesis, and the smallest next check. Change one relevant component for a follow-up experiment.

For context-window sizing, read `max_context_tokens` in each local `index.jsonl` row: it is the largest single model call (prompt plus completion). The rollout total is `tokens`; missing usage is unknown.

Finish with the supported comparison, important limitations, and a concrete next step. Reading results does not authorize retrying, publishing, or starting another evaluation. Missing evidence is a gap to report, not permission to rerun.
